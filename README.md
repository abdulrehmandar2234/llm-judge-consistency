# llm-judge-consistency

**How stable is an LLM's ranking when nothing about the task has changed?**

A small, reproducible experiment that ranks synthetic résumés against job descriptions and measures how much the ranking moves when you vary things that *should not* matter: running the same prompt again, shuffling the order candidates are listed in, raising the temperature, and rewording the prompt without changing the task.

> **Status: harness complete, experiments not yet run.** The code, corpus and metrics are finished and tested end-to-end. `results/` is empty on purpose — this README will not carry numbers until they come from a real run. See [Findings](#findings).

---

## Why this

LLMs are increasingly used as rankers and judges — of candidates, of documents, of other models' outputs. A ranking is only useful if it is *reproducible*: if re-running the same screening tomorrow reshuffles the shortlist, the ranking is measuring the sampler as much as the candidates.

That failure is invisible in normal use. You see one ranking, it looks sensible, and you act on it. You never see the four other rankings the same prompt would have produced. This repo makes those other rankings visible and puts a number on the disagreement.

I ran into this problem building candidate screening at work, at a scale where re-running was expensive and nobody could tell whether a changed shortlist meant changed candidates or changed sampling. This is the small, clean version of that question.

## What it measures

Four conditions, each run five times per job, against a fixed corpus of 18 candidates and 3 jobs:

| Condition | Prompt | Temperature | Candidate order | Compared against |
|---|---|---|---|---|
| `base` | A | 0.0 | fixed | itself (run-to-run) |
| `shuffled` | A | 0.0 | reshuffled per run | `base` |
| `temp07` | A | 0.7 | fixed | `base` |
| `variant_b` | B (reworded) | 0.0 | fixed | `base` |

`base` is the shared control, so only one condition has to be re-run when a single comparison changes. That's 4 × 5 × 3 = **60 API calls** for a full sweep.

Three metrics, because they fail differently:

- **Kendall's tau-b** and **Spearman's rho** — whole-list agreement between two rankings. 1.0 is identical, 0.0 is what two independent shuffles score.
- **Top-5 overlap** — the fraction of the shortlist two runs share. This is the one that maps to a real decision. Two runs can sit at tau = 0.85 and still disagree about who gets an interview.
- **Rank spread** — the widest position swing any single candidate shows across identical runs, which locates *where* the instability lives. High tau with a large max swing means the model is confident at the ends of the list and guessing in the middle.

Plus a **presentation-order correlation** over the shuffled runs: the correlation between the slot a candidate was shown in and the rank it received. Near zero means order was ignored; positive means candidates shown earlier were ranked better, a primacy effect.

## The corpus

18 synthetic candidates × 3 job descriptions (Senior Backend Engineer, ML Engineer, Frontend Engineer), all generated by [`data/generate.py`](data/generate.py) from a fixed seed.

**No real people.** Candidates are assembled from templated experience bullets across nine archetypes (strong/mid fits for each job family, plus generalists, a junior, and a career changer). Names are arbitrary first/last pairings; companies and universities are invented.

Two deliberate design choices:

- **The corpus is small.** The question is about the *stability* of a ranker, not its accuracy, and stability shows up in ~30 pair comparisons per condition.
- **The middle of the list is genuinely ambiguous.** Archetype weights are tuned so that several candidates are close to equally plausible for each role. A corpus where the right answer is obvious would report near-perfect stability and tell you nothing.

The archetype label is recorded in `candidates.json` for inspection but is **not** used as ground truth anywhere in the metrics — none of these experiments need to know who the "correct" best candidate is, only whether the model agrees with itself.

## Running it

```bash
git clone https://github.com/abdulrehmandar2234/llm-judge-consistency
cd llm-judge-consistency

python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env     # then add your OPENAI_API_KEY
```

Inspect exactly what will be sent before spending anything:

```bash
python src/rank.py --dry-run
```

Run the sweep, then the analysis:

```bash
python src/rank.py         # 60 calls; appends to results/runs.jsonl
python src/evaluate.py     # -> results/metrics.json, results/summary.md
python src/plots.py        # -> results/*.png
```

`rank.py` is **resumable**. Every call appends one line to `results/runs.jsonl`, and re-running skips any `(job, condition, replicate)` already recorded — an interrupted sweep picks up where it stopped without re-spending on completed calls. To re-run a condition, delete its lines.

Useful flags:

```bash
python src/rank.py --only base,temp07      # subset of conditions
python src/rank.py --job job_ml            # single job
python src/rank.py --model gpt-4o          # a different model
python src/rank.py --replicates 10         # more runs per condition
```

Rough cost for the default sweep on `gpt-4o-mini`: 60 calls at roughly 4–5k prompt tokens each. Well under a dollar at current pricing. On `gpt-4o` expect it to be a couple of orders of magnitude more.

## How the code is laid out

```
data/generate.py      corpus generator (seeded); writes candidates.json + jobs.json
prompts/              system.txt, variant_a.txt, variant_b.txt
src/conditions.py     the four conditions and the comparisons between them
src/rank.py           runs conditions against the API, appends to results/runs.jsonl
src/metrics.py        rank-agreement maths; pure functions, no IO
src/evaluate.py       runs.jsonl -> metrics.json + summary.md
src/plots.py          metrics.json -> charts
notebooks/analysis.ipynb   exploratory pass the summary table flattens away
```

One design decision worth calling out: **malformed replies are recorded, not retried away.** If the model drops a candidate, duplicates one, or invents an id, `rank.py` stores the reply with its issues rather than silently asking again. `evaluate.py` then excludes those runs from the correlations and reports the count separately. How often a judge fails to return a complete ranking is a result, and retrying until the output parses would hide it.

## Findings

*Not yet written.* The harness is complete and tested end-to-end, but the sweep has not been run, so there are no numbers to report. Publishing a plausible-looking table here without having run the experiment would defeat the entire point of the repo.

Once `python src/evaluate.py` has run, `results/summary.md` contains the generated table and this section gets the interpretation: what the numbers mean, which of the four variables mattered most, and — most importantly — anything that contradicted the expectation going in.

### What I expect to find, stated in advance

Recording these before running, so the findings can be checked against them rather than rationalised after the fact:

1. **Temperature 0 will not give identical rankings.** Greedy decoding is not deterministic across calls in practice, and near-tied candidates should flip.
2. **Shuffling candidate order will move the ranking more than temperature does.** Position effects in long-context list tasks are well documented, and 18 résumés is a long prompt.
3. **Top-5 overlap will look worse than Kendall's tau suggests.** Whole-list correlation is dominated by the easy ends of the list; the shortlist boundary is exactly where the model is least sure.
4. **The rank spread will be concentrated in mid-scoring candidates**, not spread evenly.

If these turn out to be wrong, that is the more interesting result, and it goes in the findings unedited.

## Limitations

These apply regardless of what the numbers come out at:

- **One model, one provider.** Results describe the model that was run, not LLMs generally.
- **Synthetic résumés.** Template-generated text is more uniform than real CVs — real ones have formatting noise, gaps and irrelevant detail that would likely *increase* instability. Treat any stability measured here as an optimistic bound.
- **No ground truth, so no accuracy claim.** This measures self-consistency only. A model can be perfectly consistent and consistently wrong; nothing here would detect that.
- **Small n.** 5 replicates gives 10 within-condition pairs per job. Enough to see a large effect, not enough for a tight confidence interval on a small one.
- **Shuffling is confounded with content position.** A reshuffle changes which candidate sits next to which, not only its absolute slot. Isolating the two would need a design that holds neighbours fixed.
- **The corpus encodes my assumptions** about what a strong candidate looks like, in the archetype weights. Those assumptions aren't measured here.

## Open questions

The ones I'd want to pursue properly:

- Does self-consistency predict agreement with human raters, or are they independent axes?
- Does asking for reasoning before the ranking stabilise it, or just produce a confident post-hoc justification for an equally unstable order?
- Is ranking a full list less stable than repeated pairwise comparisons aggregated into an ordering, at matched token cost?
- Can a model's own score gaps be calibrated into a usable "trust this ordering above threshold X" rule?
- How does instability scale with list length — is 18 candidates already past the point where position effects dominate?
